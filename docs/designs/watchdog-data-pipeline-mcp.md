## Problem Statement

Продакт-менеджеры тратят десятки часов в месяц на ручной анализ чужих Telegram-чатов и клиентские интервью, ловя только верхушку айсберга: недовольство, идеи, JTBD-сигналы. 80% полезной информации в переписке остаётся незамеченной или замеченной слишком поздно.

## Demand Evidence

Три конкретных сценария использования, подтверждённых внутренней потребностью:
- **Недовольство** — ловить массивы негатива по фичам, взвешивать интенсивность
- **Идеи** — вытаскивать предложения улучшений из чатов как источник для бэклога
- **Sales points** — выявлять JTBD-данные в переписке для построения маркетинговых тезисов

Потребитель определён: продакт-менеджер внутри компании.

## Status Quo

Продакты читают чаты вручную (заходят, скроллят, ищут) и проводят клиентские интервью. Это работает, но:
- Масштабируется только линейно (больше чатов = больше часов)
- Ловит только то, что ищут — упускает неожиданные сигналы
- Нет истории — нельзя посмотреть тренд за месяц/квартал
- Нет оперативности — негатив обнаруживается через дни, не часы

## Target User & Narrowest Wedge

**Потребитель:** продакт-менеджер, который принимает решения о приоритетах фич и маркетинговых месседжах.

**Narrowest wedge (демо через 2 недели):** MCP-сервер, подключённый к конкретному чату. Продакт задаёт вопрос на естественном языке («что люди говорят про онбординг?») → получает ответ с цитатами из переписки. Один чат, один вопрос, один ответ — но с реальными данными.

## Constraints

- Telegram MTProto авторизация (api_id + api_hash + номер телефона)
- Пассивное наблюдение — никаких исходящих действий, минимум риск бана
- Стабильный IP для сессии (VPS, не локальная машина)
- Один конкретный чат для первой итерации
- Интрапренёрство — нужен спонсор внутри компании
- **Только юзербот** — Telegram Business API легален, но ограничен; для мониторинга чужих чатов альтернатив нет

## Premises

1. **tg-archive в Docker** — data pipeline, наружу торчат только конфиги и SQLite через volumes
2. **MCP-сервер на Python** — второй слой, читает SQLite и отдаёт MCP tools. Один стек с tg-archive
3. **Агенты и скиллы — вне Docker** — живут на стороне MCP-клиента (Claude, кастомный UI)
4. **Первый шаг — data pipeline + MCP** — агент подключается вторым шагом, когда данные уже текут
5. **Воспроизводимость с первого дня** — Docker Compose, не локальные запуски
6. **Один чат для демо** — нужно выбрать чат, где есть активность и реальные сигналы

## Approaches Considered

### Approach A: Python MCP-сервер (выбран)
  Summary: Python-скрипт с `mcp` SDK, читает SQLite от tg-archive, отдаёт MCP tools. Один стек, один репозиторий.
  Effort:  S
  Risk:    Low
  Pros:    Один стек с tg-archive. Быстрая сборка. MCP даёт подключение к Claude/ChatGPT из коробки.
  Cons:    Python MCP SDK менее зрелый, чем TypeScript — меньше examples в интернете.

### Approach B: TypeScript MCP-сервер (отклонён)
  Summary: Node.js на `@modelcontextprotocol/sdk`. Более зрелый SDK, но два стека в Docker Compose.
  Rejection reason: два стека усложняют поддержку, выигрыш в SDK зрелости не стоит overhead

### Approach C: Без MCP — SQL + скрипт (отклонён)
  Summary: Только Docker с tg-archive, SQL-запросы для демо. MCP вторым шагом.
  Rejection reason: менее впечатляющее демо, MCP всё равно придётся добавлять — лучше сразу

## Recommended Approach

**Approach A: Python MCP-сервер**

### Docker Compose (2 контейнера)

1. **tg-archive** — cron-based sync, Telegram session, SQLite volume
2. **watchdog-mcp** — MCP server на Python, читает тот же SQLite volume

### MCP-транспорт

**stdio** для v1 — стандарт для Claude Desktop. SSE отложен до появления удалённых клиентов.

**Claude Desktop config** (`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "watchdog": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "--network", "watchdog_default", "watchdog-mcp"]
    }
  }
}
```

Для SSH-доступа к VPS — `ssh user@vps docker run -i ...` в args.

### SQLite

`PRAGMA journal_mode=WAL;` в init-скрипте tg-archive. MCP читает без блокировок записи.

### tg-archive

Зафиксировать `knadh/tg-archive` — использовать последний стабильный релиз (проверить `git tag` при реализации, записать в Dockerfile). Если тегов нет — зафиксировать commit SHA.

### SQLite Schema (из tg-archive)

tg-archive создаёт следующие таблицы (схема может отличаться в зависимости от версии — проверить при реализации):

```sql
-- Ключевые таблицы
CREATE TABLE messages (
    id INTEGER PRIMARY KEY,
    chat_id INTEGER,
    sender_id INTEGER,
    date TIMESTAMP,
    text TEXT,
    reply_to_msg_id INTEGER,
    -- ... media, forward info
);

CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    username TEXT,
    first_name TEXT,
    last_name TEXT,
    bio TEXT,
    -- ... avatar, status
);

CREATE TABLE chats (
    id INTEGER PRIMARY KEY,
    title TEXT,
    type TEXT,  -- group/supergroup/channel
    -- ... description, participants count
);
```

### FTS5 Setup

FTS5-индекс создаётся в init-скрипте watchdog-mcp при первом запуске:

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts USING fts5(
    text, sender_id, date,
    content='messages', content_rowid='id'
);

-- Populate при создании
INSERT INTO messages_fts(messages_fts) VALUES('rebuild');

-- Trigger для поддержания актуальности
CREATE TRIGGER IF NOT EXISTS messages_ai AFTER INSERT ON messages BEGIN
    INSERT INTO messages_fts(rowid, text, sender_id, date)
    VALUES (new.id, new.text, new.sender_id, new.date);
END;
```

Запускается один раз при старте MCP-сервера. Idempotent (`IF NOT EXISTS`).

### Конфигурация tg-archive

Переменные окружения в `docker-compose.yml`:

```yaml
environment:
  TG_API_ID: "${TG_API_ID}"
  TG_API_HASH: "${TG_API_HASH}"
  TG_PHONE: "${TG_PHONE}"
  TG_CHAT_IDS: "${TG_CHAT_IDS}"  # comma-separated для v1 — один ID
```

Значения в `.env` файле (не в git). Первый запуск: `docker compose run --rm tg-archive --new` — интерактивный ввод SMS-кода.

### MCP Tools — v1 (демо)

Три инструмента для первого демо. Работают только с одним чатом (параметр `chat` зарезервирован для v2).

| Tool | Parameters | Returns |
|------|-----------|---------|
| `search_messages` | `query: str` (FTS5 full-text), `date_from: str?` (ISO 8601: `2024-01-01` или `2024-01-01T10:00:00`, UTC), `date_to: str?`, `limit: int = 50` | `list[Message]` (id, text, author_id, date, reply_to_id) |
| `get_user_profiles` | `limit: int = 100` | `list[User]` (id, username, first_name, last_name, bio) |
| `get_chat_stats` | `period: str` (day/week/month, calendar-based UTC) | `Stats` (message_count, active_users, top_authors: list из 10 авторов) |

Поиск использует **SQLite FTS5** — встроенный полнотекстовый индекс, не требует внешних зависимостей.

### MCP Tools — v2 (после демо)

Signal-detection tools требуют LLM-интеграцию и prompt engineering. Отложены до решения Open Question 4.

- `get_dissatisfaction_signals(query)` — кластеры негатива (LLM classification)
- `get_idea_signals(query)` — предложения и фич-реквесты (LLM extraction)
- `get_jtbd_signals(query)` — jobs-to-be-done из переписки (LLM extraction)

## Open Questions

1. **Какой чат для первого демо?** — нужен активный чат с реальными сигналами, который продакт-менеджер уже знает
2. **Прокси для стабильности?** — Telegram может банить по IP. Прокси снижает риск, но добавляет сложность
3. **LLM для анализа — какой?** — Anthropic Claude (через API), OpenAI, локальная модель? Влияет на cost и latency. Нужно решить перед реализацией v2 signal tools

## Session Management

- **Session file** хранится в named Docker volume `session_data` (не bind mount — переносимо между VPS)
- **Первый запуск:** `docker compose run --rm tg-archive --new` → ввод номера телефона и SMS-кода в терминале
- **Re-авторизация:** при истечении сессии tg-archive падает с ошибкой; решение — ручной `--new` заново. Автоматический re-auth отложен (добавляет сложность без ценности для демо)
- **FloodWait:** tg-archive логирует rate limit ошибки; при частых повторах — алерт в stdout (видно в `docker compose logs`)

## Error Handling

- **Sync failure:** tg-archive retry через cron (следующий запуск через час). Пропуски видны в логах (`docker compose logs tg-archive`) — не нужен отдельный счётчик для v1
- **MCP при устаревших данных:** если последний sync >6 часов назад, tool возвращает предупреждение `data_stale: true` в response. MCP проверяет `mtime` файла SQLite
- **Нет данных:** tool возвращает пустой список, не ошибку. Агент видит «0 сообщений» и формулирует ответ соответственно

## Security

**Без аутентификации для v1.** MCP-сервер слушает stdio — доступ только у того, кто может запустить контейнер. Это внутренняя сеть компании, доверенная среда.

При переходе к SSE (v2) — добавить API key или OAuth.

## Success Criteria

- **Неделя 1:** tg-archive в Docker, сессия стабильна, SQLite содержит сообщения и профили одного чата. Синхронизация работает 7 дней без ошибок.
- **Неделя 2:** MCP-сервер отвечает на `search_messages`, `get_user_profiles`, `get_chat_stats`. Claude Desktop подключён и выдаёт ответы с цитатами.
- **Демо:** агент отвечает на вопрос продакта с цитатами из конкретного чата. Спонсор сказал «продолжай» — получен ресурс на развитие.
- **MCP tools:** все три v1 tool'а отвечают за <2 секунды

## Distribution Plan

**Для интрапренёрства:** Docker Compose на внутреннем VPS. Доступ через MCP-конфиг в Claude Desktop у продакт-менеджера.

**Деплой:** `docker build` + `scp` на VPS. CI/CD (GitHub Actions + registry) отложен до появления второго потребителя.

**Потребитель получает доступ** через:
1. `docker compose up -d` на VPS
2. Настройка MCP-сервера в Claude Desktop (один JSON-файл)
3. Чат с агентом = использование системы

## Data Retention

SQLite растёт с каждым sync. Для v1 — без ограничений (демо на одном чате, объём предсказуем).

Для v2 — описать retention-политику: хранить N дней активных данных, архивировать старое в отдельный файл или отложить решение, пока объём не станет проблемой.
